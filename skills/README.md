# Skills of the FilterMate agent — the standard

A skill is the instructions for one kind of task, loaded by the agent when the task comes (`load_skill`) instead of
being sent with every request. The same text is served by the MCP server of the plugin as a prompt, and exported as an
Agent Skill for an application connected to it (`skills/export/`, generated).

## Layout

```
skills/
  README.md              this standard
  <name>/
    SKILL.md             the header, then the instructions
    evals.json           its cases for scripts/agent_eval.py
  export/                generated by scripts/export_agent_skills.py (not shipped in the plugin zip)
```

The folder is the name of the skill.

## SKILL.md

```
---
name: configuration
title: Configure FilterMate
description: one line saying when to load it (shown in the list of load_skill and of the MCP prompts)
metadata:
  version: 1
  plugin_min: 5.1.0
  audience: chat, mcp
  tools: describe_settings, get_setting, change_settings
  risk: change
  trust: builtin
  requires: run_pyqgis
---

# Title

The instructions, in English, for the model.
```

| Key | Rule |
|---|---|
| `name` | 2 to 40 lower case letters, digits or dashes; the name of the folder |
| `title` | a few words |
| `description` | 300 characters at most: when to load it |
| `version` | a whole number, raised at each change of the instructions |
| `plugin_min` | the first version of FilterMate the skill is written for |
| `audience` | `chat` (offered by `load_skill`), `mcp` (served as a prompt and exported), or both |
| `tools` | every tool the instructions name: each must exist for the audience |
| `risk` | `read` (the skill only reads) or `change` (it leads to changes the levels of autonomy ask) |
| `trust` | `builtin` for the skills shipped here; a skill from elsewhere is given its trust by where it comes from, never by its own header |
| `requires` | tools that must be offered for the skill to be offered (`run_pyqgis`: the expert mode) |

The header is read without YAML: `key: value` lines, and indented `key: value` lines under `metadata`; lists are
comma separated. Any other key is refused.

## The instructions

- English, short sentences, for the model; 9,000 characters at most (about 2,300 tokens per load).
- A method first (how to work), then what never to do, then where to look.
- Name only tools and settings that exist: the tests check every tool of `tools` and every `APP.` path.
- Never tell the model to get around a refusal, a confirmation, a level of autonomy or a protected layer, nor to use
  `run_pyqgis` for what a tool refuses. A sentence that names such a thing says never.
- A skill gives no right: the tools it names stay under the levels of autonomy, the rules of the Tools tab and the
  protected layers.

## evals.json

For a skill of the chat: `{"cases": [...]}` in the format of `scripts/agent_eval_cases.json`, three cases at least,
one of them a trap (marked
`"trap": true`: what the model must not do, with `forbid`; `"expert": true` turns the expert mode on). A skill of
audience `mcp` alone is not played by the bench of the chat. Run offline with `python scripts/agent_eval.py`, and live
before a change of a skill that matters (see `docs/AGENT_MODE.md`).

## Skills from elsewhere

Skills in the folder `FilterMate/skills` of the QGIS profile (trust `user`) and in the folder `filtermate_skills` next
to the open project file (trust `project`) follow the same layout (`adapters/agent/skill_sources.py`). They are data,
not instructions of FilterMate:

- their trust comes from where they are, never from their header; a name of a skill of the plugin is refused, and a
  project cannot replace a skill of the profile;
- the folder of a project is the one next to its file, whatever home path the project sets;
- one that does not follow this standard, is over 64 KB, is a link to another place (the sub-folder, its `SKILL.md`
  or the skills folder itself, told before it is followed) or holds a character that does not show on screen
  (controls, format characters, the default ignorable code points of Unicode such as the tags, the variation
  selectors and the fillers of Hangul, code points with no character yet, separators of lines) is left out, the
  others are kept. Kept, one or two together: the zero width joiner and non-joiner, the marks of the direction (the
  Arabic letter mark too), the soft hyphen and the selectors of the look of an emoji; and the flags of England,
  Scotland and Wales, the only sequences of tags kept. The log gives the reason, never the words of the skill (the
  log reaches the model through `diagnose_performance`);
- spaces at the end of a line are taken away and three empty lines in a row become two, in what the user reads and
  in what the model receives alike; the question wraps every line;
- 20 of them at most are offered (`MAX_EXTRA`), the profile first; a folder of more than 200 entries (files too) is
  not read;
- the user reads all of it and allows it before it is loaded the first time: its name, title, description,
  `requires` and instructions (`skills.shown`), which is all the model may receive of it. The allowance is kept by
  the fingerprint of that text and of its folder, so a change of either is asked again;
- until then the list of `load_skill` gives its name (2 to 40 letters, digits and dashes) and where it comes from,
  with none of its other words; a no is not asked again until QGIS restarts or the skill changes; once allowed
  its description is listed, said to be from elsewhere;
- loaded, it comes after a note saying where it comes from and that it gives no right;
- it guides the chat only, its `tools` ignored, its `requires` kept. Another application is never served it nor
  asked about it: the `load_skill` of the MCP server lists the skills of audience `mcp` that its own tools allow,
  as its prompts do.

## Families of tools

With the option *Offer the tools of a task once the agent loads its instructions* (on by default), the tools a skill
of the plugin names in `tools` or `requires` are left out of the requests until the agent loads that skill; the tools
that filter and read (`FILTERING_TOOLS`) and `load_skill` are always offered (`core/agent/families.py`). Name in
`tools` every tool the task needs: a tool left out of it stays hidden while the skill guides the model.

## Checks

`tests/unit/agent/test_skills_standard.py` applies these rules to every skill here; `scripts/export_agent_skills.py
--check` fails when `skills/export/` is out of date.
